# ADR: AKBSM Draft Proposal Review Lifecycle

## Status

Proposed / design-only.

This ADR defines a future lifecycle for temporary AKBSM draft proposals. It
does not implement proposal review lifecycle, proposal storage, AKBSM writes,
proposal persistence, permanent associations, relation type creation, concept
creation, behavior influence, Mode C behavior, PolicyPressureReview influence,
or marker 36.

## Context

`v0.0.6` marks the controlled AKBSM probe draft proposal experiment checkpoint.
At that checkpoint, `AKBSMAssociationProbe` can create temporary metadata-only
proposals only through an explicit test/scenario enabled provider path. Normal
runtime remains disabled/no-op, no proposal commit path exists, no proposal
persistence exists, and AKBSM writes remain blocked.

Before any storage, review queue, commit behavior, or permanent AKBSM write is
considered, draft proposals need a bounded lifecycle vocabulary that cannot be
confused with approval to mutate memory.

## Decision

Future AKBSM draft proposals should have a lifecycle before any storage,
commit, or permanent AKBSM write is considered.

The lifecycle must remain temporary and metadata-only. Review means classifying
the temporary proposal. Review does not mean approving a memory write, changing
behavior, changing scoring, creating a concept, creating a relation type, or
updating AKBSM.

No lifecycle state may imply AKBSM mutation.
No lifecycle state may imply proposal commit.
No lifecycle state may allow permanent storage.

## Lifecycle states

- `created`: proposal was generated by the allowed source.
- `review_pending`: proposal is waiting for review/inspection.
- `accepted_for_observation`: proposal may be kept temporarily as an
  observation, not committed.
- `deferred`: not enough evidence yet; keep only temporarily if allowed by
  future policy.
- `rejected`: proposal should not be used.
- `expired`: proposal lifetime ended.

These states are metadata labels only. They do not create AKBSM relations,
concepts, relation types, storage records, behavior pressure, scoring inputs,
guard inputs, Mode C advisory inputs, or writer inputs.

## Allowed transitions

Allowed future transitions:

- `created -> review_pending`
- `review_pending -> accepted_for_observation`
- `review_pending -> deferred`
- `review_pending -> rejected`
- `review_pending -> expired`
- `accepted_for_observation -> expired`
- `deferred -> review_pending`
- `deferred -> expired`
- `rejected -> expired`

All transitions are metadata-only.

## Forbidden transitions

Forbidden transitions:

- `created -> AKBSM write`
- `review_pending -> AKBSM write`
- `accepted_for_observation -> AKBSM write`
- `deferred -> AKBSM write`
- `rejected -> AKBSM write`
- `expired -> AKBSM write`
- `any state -> commit/apply/save/write/persist/mutate`

Forbidden write-like lifecycle state names and meanings:

- `committed`
- `applied`
- `persisted`
- `written`
- `saved`
- `accepted_for_write`
- `ready_to_write`
- `approved_for_akbsm`

No lifecycle state may imply AKBSM mutation.
No lifecycle state may imply proposal commit.
No lifecycle state may allow permanent storage.

## Review semantics

Review means classifying the temporary proposal.

Review does not mean approving a memory write.
Review does not mean changing behavior.
Review does not mean changing scoring.
Review does not mean creating a concept.
Review does not mean creating a relation type.
Review does not mean updating AKBSM.

`accepted_for_observation` means only that the proposal may remain available as
temporary metadata for observation. It is not AKBSM write approval.

## Expiration semantics

Proposal lifetime must be bounded.

A future implementation must define at least one of:

- tick TTL
- scenario/session lifetime
- context retention expiry
- explicit review expiry

Expired proposals must not be revived into writes.

## Storage policy

Allowed future storage:

- temporary ContextMemory metadata
- scenario/debug output
- test-local provider return values

Forbidden storage:

- `Memory/AKBSM/*`
- `Memory/ExpSM/*`
- `semantic_core.json`
- `technical_feedback_patterns.json`
- permanent proposal files
- permanent association files

## Memory safety requirements

The lifecycle must preserve current memory safety:

- no AKBSM mutation
- no ExpSM mutation
- no proposal persistence
- no proposal commit/apply/save/write/persist/mutate path
- no permanent AKBSM associations
- no relation type creation
- no concept creation
- no behavior, scoring, guard, Mode C, PolicyPressureReview, ExpSM writer,
  AKBSM writer, or memory writer integration
- marker 36 remains absent
- real ExpSM and AKBSM hashes remain unchanged in safety checks

## Required future scenario coverage

Before implementation, future scenario coverage must prove:

- proposal starts as `created` / `review_pending`
- proposal can become `accepted_for_observation` without AKBSM write
- proposal can become `deferred` without AKBSM write
- proposal can become `rejected` without AKBSM write
- proposal can expire without AKBSM write
- `accepted_for_observation` does not affect behavior/scoring/guards
- expired proposal cannot be committed
- rejected proposal cannot be committed
- normal runtime still creates no proposals by default
- disabled proposal scenarios still pass
- controlled AKBSMAssociationProbe experiment still passes

## Required future verifier coverage

Future verifier coverage must:

- verify lifecycle states exist only as metadata
- verify forbidden write-like states do not exist
- verify allowed transitions only
- verify forbidden transitions absent
- verify no commit/apply/save/write/persist/mutate methods
- verify no permanent proposal persistence
- verify no AKBSM mutation
- verify no ExpSM mutation
- verify no behavior/scoring/guard/Mode C integration
- verify marker 36 absent
- verify memory hashes unchanged

## Rejected alternatives

- direct proposal commit
- `accepted_for_write` state
- persistent proposal queue
- automatic AKBSM write after review
- PolicyPressureReview-driven review
- Mode C-driven review
- DecisionSelector-driven review
- ActionScoring-driven review
- ValueFeedback-driven review

These alternatives are rejected because they are too close to behavior
pressure, write paths, scoring/selection pressure, review-to-write ambiguity,
or permanent memory mutation.

## Consequences

This ADR creates vocabulary for future review work without approving an
implementation. It keeps the current controlled proposal experiment temporary,
metadata-only, source-limited to `AKBSMAssociationProbe`, and disconnected from
normal runtime behavior and memory writes.

Any future lifecycle implementation must update scenarios and verifiers before
or with code changes, and must still keep write-like behavior forbidden unless
a later ADR explicitly changes AKBSM write policy.

## Next steps

Review this ADR before any lifecycle implementation pass.

Stop before proposal storage, proposal review lifecycle implementation, writer
wiring, behavior wiring, Mode C wiring, or permanent AKBSM mutation.
